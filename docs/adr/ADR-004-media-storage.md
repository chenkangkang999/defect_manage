# ADR-004：图片存储用 Django MEDIA_ROOT，不引入对象存储

| 项目 | 内容 |
|---|---|
| 状态 | ✅ Accepted |
| 决策日期 | 2026-10-24 |

## 背景

每条检测记录都带两张图：原图（`original/`）与标注图（`defect_img/`）。图片由检测环节
产出后上传到本系统，用于人工复核与事后追溯。系统的使用者规模小（厂内几人到几十人），
部署环境是产线旁的普通 PC 或内网服务器。

## 备选方案

- 方案 A：Django `ImageField` + `MEDIA_ROOT`（本地磁盘），开发模式由 Django 直接托管
- 方案 B：独立对象存储（MinIO / 阿里云 OSS / S3），数据库只存 key
- 方案 C：图片存进数据库（BLOB）

## 决定

方案 A：`ImageField(upload_to="original/")` 与 `ImageField(upload_to="defect_img/")`，
落盘到 `MEDIA_ROOT = BASE_DIR / "media"`，`MEDIA_URL = "/media/"`。

`MEDIA_ROOT` 由 `BASE_DIR` 推导 —— **不写死盘符**，换机器/换目录都不用改代码。

## 理由

1. **规模匹配**：单机几十 GB 的图片量，本地磁盘完全够用，且没有网络依赖（产线环境网络不稳）。
2. **备份简单**：`db.sqlite3` + `media/` 两个路径复制走即可，运维不需要懂对象存储。
3. **迁移成本低**：`ImageField` 的存储后端是 Django 的 `STORAGES` 配置项，
   将来要换 OSS/S3 只需改配置 + 写一个 storage class，模型与视图不用动。
4. **避免 BLOB**：图片进库会让 SQLite 文件迅速膨胀、备份变慢、迁移困难。

## 后果

- 正面：零外部依赖；本地开发与生产行为一致；备份/恢复是一条 `Copy-Item`。
- 负面：**多实例部署会出问题**（每台机器各有自己的 `media/`）；
  Django 直接托管 `media/` 只适合开发模式，生产应由 Nginx 托管或走 `whitenoise` 类方案。
- 负面：磁盘满会导致上传失败，需要监控——已在手册「运维」一节写明检查项。
- 中性：文件名沿用上传时的名字，可能与检测环节的产物名重复；如需强约束应在视图层加前缀。

## 撤销条件

- 需要多实例/容器化横向扩容；
- 图片总量超过单盘容量，或需要跨厂区共享；
- 出现合规要求（图片必须存于指定存储、需版本化与生命周期策略）。
