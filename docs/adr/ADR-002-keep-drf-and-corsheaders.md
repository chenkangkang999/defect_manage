# ADR-002：保留 DRF 与 corsheaders 依赖，但仍走传统路由

| 项目 | 内容 |
|---|---|
| 状态 | ✅ Accepted |
| 决策日期 | 2026-10-24 |

## 背景

项目初始版本就在 `INSTALLED_APPS` 里装了 `rest_framework`、`corsheaders`，
并配了 `CorsMiddleware` 与 `CORS_ALLOW_ALL_ORIGINS = True`，但**当前没有任何 API 视图、
序列化器或 DRF 路由**（`defect/urls.py` 只有 5 条传统 CRUD 路由）。

一次回退（revert）把曾经写过的 DRF 接口层（`api_views.py`、`serializers.py`）撤销了，
于是出现"依赖留着、实现没了"的状态，需要明确这是有意为之还是遗漏。

## 备选方案

- 方案 A：把 DRF 与 corsheaders 从依赖和 `INSTALLED_APPS` 里一并摘掉，保持最小依赖
- 方案 B：保留依赖与中间件，暂不写 API，等需要时直接加（本决策）
- 方案 C：立刻把 API 层补回来

## 决定

方案 B：**保留**依赖与全局跨域配置，暂不提供 API。

## 理由

1. 这两项是**初始版本就有的既定选择**，不是本次回退引入的临时状态；摘掉属于改变历史决策，
   需要单独的理由（目前没有）。
2. 保留的代价很低：两个纯 Python 包，不影响启动与运行。
3. 预期的下一步（看板、复核队列、SSE 实时进度）几乎必然需要一个 JSON 接口层，
   届时不必重新引入依赖、改中间件、调 CORS —— 直接加视图即可。
4. 跨域放开目前只在开发环境有意义；生产环境的收紧方式见 ADR-003（走环境变量）。

## 后果

- 正面：未来加 API 零门槛；前后端分离的客户端可直接联调。
- 负面：**当前存在"配置了但没用到"的迷惑性**——读代码的人可能以为有接口。
  已在 README 的「当前状态」与功能表中写明"尚无 API 层"。
- 安全：`CORS_ALLOW_ALL_ORIGINS = True` 绝不能带到生产；现已改为由
  `DJANGO_CORS_ALLOW_ALL` 控制，默认值保持开发友好。

## 撤销条件

- 若确认永远不做 JSON 接口（纯服务端渲染到底），摘掉这两个依赖；
- 若做接口，则本 ADR 由"接口层设计"的新 ADR 取代，并在此标注 Superseded。
