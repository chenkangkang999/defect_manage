# ADR-001：技术栈与服务端渲染的单体结构

| 项目 | 内容 |
|---|---|
| 状态 | ✅ Accepted |
| 决策日期 | 2026-10-22 |

## 背景

缺陷检测结果的台账管理需要一个能快速录入、查看、筛选的 Web 界面，使用者是产线检测
人员与质检管理员。项目初期只有一个人开发，没有前端工程师，也没有独立部署前端的运维成本预算。

## 备选方案

- 方案 A：Django + 服务端模板（Django Template）单体应用
- 方案 B：Django REST Framework 提供接口 + 前端 SPA 前后端分离
- 方案 C：Flask/FastAPI + 轻量前端

## 决定

方案 A：Django + 服务端模板，单仓单应用（`defect` app + `defect_manage` 项目配置）。

## 理由

1. **交付速度**：录入表单、列表、详情、编辑、删除五类页面都是 Django 的强项，
   `ModelForm` + 通用视图几乎不需要额外代码。
2. **依赖最少**：只需要 Python 与 `requirements.txt` 里四个包，没有 Node 工具链。
3. **与检测链路的耦合点很小**：系统的核心价值在"记录 + 追溯"，推理与训练都在
   [ODPlatform](https://github.com/chenkangkang999/ODPlatform) 侧完成，本项目只负责台账。
4. **单人可维护**：一套语言、一套部署、一个数据库文件。

## 后果

- 正面：开发与部署都简单；模板里能直接复用 Django Admin，运维人员可自助维护基础数据。
- 负面：页面交互能力弱（无实时刷新、无复杂图表）；未来若要做看板/热力图这类富交互页面，
  要么引入少量 JS，要么补 API 层（见 ADR-002）。
- 中性：数据库先用 SQLite，单机够用；换 PostgreSQL 只需改 `DATABASES`。

## 撤销条件

出现以下任一情况即重新评估是否拆分前后端：

- 需要多人同时高频写入（SQLite 写锁成为瓶颈）；
- 交互复杂度显著上升（实时进度、拖拽复核、图表联动）；
- 出现第二个客户端（移动端/桌面端）复用同一套数据。
